## Why this change exists

The application now owns monetary-policy explanations. For example:

> Your requested refund of $750 is above the $500 specialist-review threshold, so it requires specialist review before it can be approved.

Those amounts come from the synthetic request and verified policy catalog, not a
retrieved document. Attaching a RAG citation would misrepresent their source.
Conversely, ordinary knowledge claims still need retrieved evidence. A model's
chosen answer purpose is not proof that its claims are application-owned.

## What gets checked

1. Before constructing provider clients, validate the reviewed expectation against
   the explicitly configured local policy. Missing, unknown or mismatched policy
   configuration must stop the run before paid work.
2. Grade the observed answer against the independently resolved policy version
   and catalog hash, reviewed amount, limits, band and exact reference text.
   The expected text must not be generated by the production renderer being tested.
3. Require zero RAG citations for this application-only answer. Wrong text,
   mismatched policy evidence or invented citations must fail the new blocking
   policy-answer grade. An `amount_review` label alone cannot make it pass.
4. Continue retrieval and RAGAS semantic grading. Retrieval evidence remains
   measured even though this particular answer draws its amounts from the
   verified catalog, recorded through version/hash provenance, not a passage.

The existing minimum-citation grader is unchanged. It remains informational in
the live runner; a failed citation check is not automatically a failed trial.
The new policy-answer grader is blocking for the explicitly reviewed case.
Prohibited-claim checks remain blocking; provisional semantic scores remain
nonblocking. Always inspect the individual grades, not just the trial pass flag.

Exact wording is appropriate here because the application renders a reviewed
deterministic template. It is not a general substitute for semantic evaluation
of freely generated answers. Mixed knowledge-and-policy answers would need both
types of evidence; this bounded case does not grant a blanket exemption.

## How to read the change

Start with the v4 fixture, then `evaluation_runner/answer_graders.py`, then
`evaluation_runner/live_rag_evaluation.py` and their focused tests, all under
`apps/services/evaluation-runner/`:

1. `read_reviewed_policy_answer()` validates the explicit case expectation.
2. `_preflight_policy_answer_authorities()` verifies it against the configured
   catalog before client construction.
3. `ReviewedPolicyAnswerGrader.grade()` checks observed output and provenance.
4. `tests/test_refund_rag_answer_v4.py` exercises success, failures and legacy
   preservation. `tests/test_refund_rag_answer_executor.py` also exercises the
   real composer/renderer and executor through the new grader with external
   retrieval/model calls replaced by offline fakes.

The flow is:

```text
Reviewed case + explicit policy configuration
    → preflight against shared catalog
    → existing retrieval and production answer composer
    → observed answer with version/hash provenance
    → deterministic policy check + existing RAGAS metrics
```

No Agent Runtime product code, token, server, refund operation or dependency
change belongs to this batch.
